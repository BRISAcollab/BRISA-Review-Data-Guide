Review Data Guide

This guide describes how to organize files while a systematic review is being conducted and how to prepare the final materials for a public repository.

The structure is designed for preclinical systematic reviews using different software and workflows. A project may use Rayyan, Covidence, DistillerSR, spreadsheets, R, RevMan, jamovi, Stata, Python, or other tools. The folder structure records what happened in the review without requiring a specific platform.

What this guide is for

During a review, the team creates more material than should appear in the final public repository. Drafts, training files, reviewer-level decisions, platform exports, working spreadsheets, and full-text PDFs may be important internally, but only part of that material is needed for public reuse.

This guide therefore uses two related structures:

  1. Internal workspace: the complete working record of the review.
  2. Public release: a smaller, documented set of files selected from the internal workspace.

How the two structures relate

1

Work inside the project workspace

Keep source files, original exports, working files, reviewer decisions, notes, scripts, and final datasets in the relevant stage folders.

→
2

Select the final materials

At publication, identify the files another researcher needs to understand the methods, inspect the data, and reproduce the analysis.

→
3

Prepare the public release

Copy and document those files in 10_PUBLIC_RELEASE, then deposit that folder in an appropriate repository.

Important: the public repository is not a copy of the internal workspace. It is a curated release created from it.

Internal workspace

The internal structure follows the stages of a review. Create only folders that are relevant to the project.

PROJECT/
├── 00_README/
├── 01_ADMIN/
├── 02_PROTOCOL/
├── 03_SEARCH/
├── 04_SCREENING/
├── 05_EXTRACTION/
├── 06_ASSESSMENT/
├── 07_ANALYSIS/
├── 08_OUTPUTS/
├── 09_MANUSCRIPT/
└── 10_PUBLIC_RELEASE/
Keep source files unchanged

Original database or platform exports should be preserved before editing, cleaning, or converting them.

Use dated snapshots when needed

Use ISO dates such as 2026-08-23 for dated versions and avoid names such as final_final2.xlsx.

Do not create empty folders

If a review does not include a given assessment or analysis step, that part of the structure can be omitted.

00

README

Project orientation and current status.

00_README/
└── README.md

The internal README should allow a new collaborator to understand what the project is, where the main files are, and which platforms are being used.

Store here

  • Project title and review question
  • Project leads and team roles
  • Current project stage
  • Protocol and registration links
  • Main software/platforms
  • Short explanation of the folder structure

Public release

Create a separate public-facing README.md describing the released files, the related publication, licenses, and how to reproduce the analysis when applicable.

Example: internal README.md

Example: screening_guide.md 
# Screening guide

## Include when
- Original preclinical study
- Relevant disease or experimental model
- Intervention matches the protocol
- At least one eligible outcome is reported

## Exclude when
- Human study
- Review, editorial, protocol, or conference abstract only
- Wrong model
- Wrong intervention

## Ambiguous cases
If model eligibility cannot be determined from the abstract, include for full-text assessment.
Example: screening_final.csv 
record_id,title_abstract_decision,full_text_decision,exclusion_reason
R0001,include,include,
R0002,include,exclude,Wrong population
R0003,exclude,,Wrong study design
R0004,include,exclude,No eligible outcome

Why keep the guide? Final decisions alone do not show how eligibility criteria were interpreted in practice. The guide documents the rules that reviewers actually used.

Example: extraction_guide.md 
# Data extraction guide

## study_id
Unique ID assigned to each included study.

## species
Report the species exactly as described by the authors.
Use "NR" when not reported.

## sample_size
Extract the number of animals contributing to the reported outcome.
Do not use the total number enrolled if attrition occurred before outcome measurement.

## outcome_source
Allowed values: table, text, figure, supplementary material, author contact.

## notes
Record any interpretation or conversion that may affect the final value.
Example: extracted_data.csv 
study_id,species,sex,sample_size,outcome,timepoint,value,unit,outcome_source

Example: decision_log.csv 
date,study_id,issue,decision,reason
2026-07-02,S014,Outcome reported as SEM,Converted SEM to SD,Needed for quantitative synthesis

Basis: PRISMA 2020 recommends stating where data collection forms and extracted data are publicly available. The separation between original entries, adjudication, and final data is a BRISA workflow recommendation for traceability.

A curated set of files prepared from the internal workspace.

The public release should contain enough information for another researcher to understand what was done and inspect or reproduce the reported results. It does not need to contain every internal file.

Choosing a repository

Choose the repository after the public release has been prepared. The same folder can be deposited in different repositories, but the repository should provide stable access, appropriate metadata, and a persistent identifier when possible.

1. Check requirements first

If the journal, funder, institution, or research community requires a specific repository, follow that requirement.

2. Prefer a suitable domain or institutional repository

If a trusted repository already serves the relevant discipline or institution, it may provide better metadata, preservation, or curation than a general repository.

3. Otherwise use a trusted general repository

Look for DOI or another persistent identifier, versioning, clear licensing, long-term preservation, adequate file limits, and accessible metadata.

Common options

RepositoryUseful whenPoints to consider
ZenodoYou need a general-purpose research repository with DOI, versioning, and GitHub integration.Good default for citable data/code releases. GitHub releases can be archived in Zenodo and assigned DOIs.
DataverseYour institution or community provides a Dataverse installation and you want dataset-focused metadata and versioning.Features and policies depend on the specific Dataverse installation.
FigshareYour institution uses Figshare or you want a general-purpose repository with DOI and versioning.Storage limits and institutional services vary.
GitHubThe main research object is code, documentation, a website, or a version-controlled workflow.Use GitHub for development and transparency; pair it with Zenodo or another repository when a DOI and archival research record are needed.
OSF RegistrationYou need a time-stamped registration or frozen record of a protocol/workflow.Useful for registration. OSF Projects are being phased out as general project workspaces and will become read-only in 2027.
Institutional or domain repositoryA suitable repository is supported by your institution or field.Often preferred when it satisfies funder, journal, discipline, preservation, and metadata requirements.

Repository selector

Use this as a starting point rather than a formal recommendation.

Answer the questions above to get a starting option.
Still unsure? Use re3data to search research data repositories by discipline, persistent identifier, access conditions, licensing, and other repository characteristics. FAIRsharing can also be used to identify repositories, standards, and data policies.

Current OSF note: COS has announced that new OSF Projects will no longer be created after November 16, 2026 and existing Projects will become read-only on February 19, 2027. Existing public content remains accessible, while OSF Registrations and Preprints continue. For new long-term data releases, do not assume OSF Projects will remain a general-purpose repository workflow.
