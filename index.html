BRISA

Review Data Guide

A folder structure for managing a systematic review project and preparing the files that will be shared in a public repository.

Scope. The guide is designed for preclinical systematic reviews. It does not require a specific screening, extraction, or analysis platform. Projects may use Rayyan, Covidence, DistillerSR, spreadsheets, RevMan, jamovi, R, Stata, Python, or other tools.

Internal workspace and public repository

The two structures have different purposes. The internal workspace keeps the working record of the review. The public release contains the files needed to understand and reuse the completed work.

Internal workspace

Used throughout the project. It may contain drafts, training files, platform exports, reviewer-level decisions, working spreadsheets, article PDFs, scripts, notes, and final datasets.

→

Public release

Prepared near publication. It contains selected final files, guides, data, code, and documentation. It is deposited in a suitable repository.

The public release is not a copy of the internal workspace. It is prepared from the internal folders after checking which files are final, interpretable, shareable, and useful to other researchers.

How to use this guide

  1. Create the internal folders that apply to your review.
  2. Store original exports and working files in the relevant stage rather than overwriting them.
  3. At publication, select the files marked for public sharing and copy them into 10_PUBLIC_RELEASE.
  4. Deposit the public release in a repository that meets the needs of the project, journal, funder, and institution.

Internal project structure

Create only the folders that apply to the review. The numbering keeps the project ordered by stage.

PROJECT/
├── 00_README/
├── 01_ADMIN/
├── 02_PROTOCOL/
├── 03_SEARCH/
├── 04_SCREENING/
├── 05_EXTRACTION/
├── 06_ASSESSMENT/
├── 07_ANALYSIS/
├── 08_OUTPUTS/
├── 09_MANUSCRIPT/
└── 10_PUBLIC_RELEASE/
File naming. Prefer descriptive names and ISO dates (YYYY-MM-DD). Preserve original exports before editing them. Avoid names such as final_final2.xlsx.

Example screening_guide.md
# Screening guide

## Include when
- Original preclinical study
- Relevant experimental model
- Intervention matches the protocol
- At least one eligible outcome is reported

## Exclude when
- Human study
- Review, editorial, protocol, or conference abstract only
- Wrong model
- Wrong intervention

## Ambiguous cases
If eligibility cannot be determined from the abstract, include for full-text assessment.
Example screening_final.csv
record_id,title_abstract_decision,full_text_decision,exclusion_reason
R0001,include,include,
R0002,include,exclude,Wrong population
R0003,exclude,,Wrong study design
R0004,include,exclude,No eligible outcome
Why share the guide? The final decisions show what was included or excluded. The guide shows how the team interpreted the eligibility criteria while making those decisions.

Choosing a repository

Prepare the public release first, then choose where it will be deposited. The repository should fit the project and any journal, funder, or institutional requirements.

Use this order

  1. Check mandatory requirements. If a journal, funder, institution, or discipline requires a repository, use that option first.
  2. Check for a suitable domain or institutional repository. Prefer it when it offers appropriate preservation, metadata, and support.
  3. Otherwise choose a trusted general repository. Compare persistent identifiers, versioning, licensing, storage, metadata, and access.
  4. Use GitHub for active version control and websites/code. For a citable archived release, pair it with an archival repository such as Zenodo when appropriate.

Repository checklist

  • Does it provide a DOI or another persistent identifier?
  • Can the deposited version remain available long term?
  • Does it support versioning for updates?
  • Can you assign a clear license?
  • Are the file size and file type limits suitable?
  • Does it provide enough metadata to describe the review?
  • Does the journal/funder accept it?
  • If access restrictions are needed, does the repository support them?

Common options

Institutional or domain repository

Best starting point when your institution, funder, journal, or research community provides or requires one.

Zenodo

General-purpose option for data, code, and supporting files. Useful for DOI-based releases and GitHub archiving.

Dataverse

Useful for dataset-focused deposits when an institutional or community Dataverse installation is available.

Figshare

General or institutional repository option for research files and datasets.

GitHub

Useful for code, version-controlled documentation, and this type of website. It is not a substitute for an archival data repository when a persistent research record is required.

OSF Registrations

Useful for time-stamped registrations and protocol records. Check current OSF policies before choosing OSF services for long-term file hosting.

Need to compare repositories? Search re3data or FAIRsharing for discipline-specific and general repositories.
