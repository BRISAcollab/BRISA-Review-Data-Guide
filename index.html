BRISA

Project Data Management and Sharing Guide

A common structure for managing preclinical systematic review and meta-analysis projects from the internal workspace to the public research record.

The guide was developed to make BRISA projects easier to understand across teams, preserve the review workflow over time, and support transparency, reproducibility, and reuse of preclinical evidence-synthesis data.

BRISA teams should begin with the Quick Start and use the detailed sections when setting up or documenting each stage. Other research groups may adapt the structure to their own platforms, repositories, and institutional requirements.

Working on a BRISA project?

Follow the required setup and storage rules in the Quick Start.

Need a file-level explanation?

Use the detailed guide for folder purposes, examples, formats, and sharing status.

Adapting the guide?

Retain the underlying documentation principles and define local institutional rules.

BRISA quick start

This section sets out the common starting point for BRISA projects. The detailed guide below explains the purpose and contents of each folder.

Official workspace. The complete working record must be stored in the project folder within the BRISA Google Drive. Files kept only in personal accounts or on local devices are not the official project record.
  1. Create or locate the project folder in the BRISA Google Drive. Confirm that the project lead and the relevant BRISA coordinators have access.
  2. Copy the blank project template. Rename the root folder with the project short name and complete 00_START_HERE/README_FIRST.md.
  3. Use the numbered folders throughout the project. Preserve original exports before cleaning, reconciling, or transforming them.
  4. Document every final dataset. Keep a data dictionary with the exact column names, definitions, allowed values, units, missing-value codes, and derivation rules.
  5. Keep final materials distinguishable from drafts and reviewer-level work. Use the final-data and public-release folders for curated files only.
  6. Prepare the public-release package before submission or publication. Do not publish restricted article PDFs, personal information, confidential records, or licensed exports that cannot be redistributed.

File formats. Working spreadsheets are supplied as .xlsx; machine-readable examples and public data use .csv; instructions use .md or .txt; analysis code uses its native format. The packages do not create duplicate official versions without a stated purpose.

Internal workspace and public repository

The two structures serve different stages of the same project.

Internal workspace

The complete working record of the review. It starts when the project starts and preserves drafts, original platform exports, training files, reviewer-level data, intermediate datasets, decisions, analysis files, and final materials.

Purpose: preserve how the work developed
→

Public repository

A curated selection prepared from the internal workspace. It contains the files another researcher needs to understand how the review was conducted, inspect the final data, reproduce analyses when applicable, and reuse the shared materials.

Purpose: make the completed work understandable and reusable
The public repository is not a copy of the full internal workspace. Drafts, training files, confidential administrative material, working copies, and restricted full-text PDFs usually remain internal. Final guides, final datasets, analysis files, and other materials needed to interpret the work are selected for public release.

File naming and formats

File names and formats should make the project understandable to someone who did not create it.

File naming

  • Use descriptive names.
  • Use ISO dates: YYYY-MM-DD.
  • Use version numbers while a document is changing.
  • Use the same terms throughout the project.
  • Preserve original exports before editing or transforming them.
Better2026-04-12_pubmed_search.risscreening_guide_v2.docxrisk_of_bias_final.csv
Avoidnew search.risguide final new.docxfinal_final2.xlsx

File formats

  • Keep the original format for platform/database exports.
  • For public tabular data, prefer .csv or .tsv when practical.
  • .xlsx is acceptable for internal work and for files that rely on multiple sheets, formulas, or validation.
  • .docx is practical for collaborative drafting; .pdf is useful for a fixed final document.
  • .md is convenient for documents maintained in GitHub, but it is not required.
  • Keep native analysis files from the software actually used.
Why this matters. A descriptive name should tell a new team member what the file contains before they open it. A stable format should allow the file to remain interpretable even if the project later changes software.

Example screening guidescreening_guide_final.pdf

Include when

  • Original preclinical study
  • Relevant experimental model
  • Intervention matches the protocol
  • At least one eligible outcome is reported

Exclude when

  • Human study
  • Review, editorial, protocol, or conference abstract only
  • Wrong model or intervention

Ambiguous cases

If eligibility cannot be determined from the abstract, include for full-text assessment.

Public repository

BRISA repository decision pending. The standard repository for future BRISA releases has not yet been selected. Prepare the complete release package in 10_PUBLIC_RELEASE/ and retain it in the BRISA Google Drive until project-specific or institutional instructions are confirmed.

Requirements for the future BRISA repository

  • Persistent identifier for the public release
  • Versioning for corrections and review updates
  • Clear licensing and file-level metadata
  • Suitable file-size and file-type limits
  • Long-term availability
  • Support for any required access restrictions
  • Compliance with journal, funder, and institutional requirements

For groups adapting this guide

Groups outside BRISA should define a repository at the institutional level rather than leaving the decision undocumented within each project. Where no standard exists, compare suitable domain, institutional, and general-purpose repositories using the requirements above. GitHub is appropriate for active code and documentation but does not replace an archival research-data record when a persistent release is required.

Institutional or domain repository

Use when an institution, funder, journal, or research community provides or requires one.

General-purpose repository

Evaluate persistent identifiers, versioning, licensing, metadata, storage limits, and preservation.

GitHub

Use for version-controlled code, documentation, and project websites. Archive a release elsewhere when required.

Repository directories

Use re3data or FAIRsharing when no institutional or disciplinary standard is available.
